# 手机在外面也能连电脑 设计

日期：2026-10-01 · 状态：设计已口头确认（直连 + 壳页面 + 安全；要 MQTT 慢速兜底；先实测再做完整版），待审阅本文

## 目标

手机不在家里 Wi-Fi 时也能用 Claude Web 的完整界面，**用户什么都不用装、不用注册、不用自己搭服务器**，项目本身也不运营服务器（以后可以加，接口留好）。在家时同样走这条路，配对一次，在哪都能用。

## 不做

- 不做原生 App，手机用浏览器（建议「添加到主屏幕」）。
- 不做自建中转服务器（以后的事，见「以后的中转」）；不做组网（Tailscale 之类要用户自己装，用户明确不要）。
- 不用免费 TURN：都要注册、凭据会暴露在开源代码里、没有国内节点。
- 不改现有局域网路径：原来的局域网二维码和 3091 入口保留，没联网时照样用。

## 调研结论（2026-10-01，报告在会话 scratchpad，结论摘要）

- Mirasim（闭源、要账号和邀请码）：先拨局域网，不在同一网络时走厂商的中转，配对码里带主机公钥做端到端加密。开源同类 Paseo / Happy / Remodex 都是「电脑主动连中转 + 扫码 + 端到端加密」，都需要有人运营中转。
- 不靠服务器只能直连：手机流量在 IPv4 上基本是对称型 NAT，打洞多半失败；但国内移动网络 IPv6 流量占比约七成，两端都有 IPv6 时 ICE 同时发包就能打通（社区普遍反映，没有可靠统计）。
- 牵线可以借公共 MQTT（broker.emqx.io 等，WSS），消息自己加密。nostr 中继在国内多数不通。
- Google STUN 国内不通；国内可用的有 stun.hitv.com（IPv6）、stun.cloudflare.com（v4 + v6）、stun.miwifi.com、stun.chat.bilibili.com，都不是官方承诺的公共服务。
- 网页托管：Gitee Pages 已下线；github.io / pages.dev 在国内时好时坏，所以壳页面要小、要被缓存，只有第一次打开依赖它。

## 总体结构

```
手机浏览器                                         公共服务（不归我们）                 电脑
┌──────────────────────────────┐                ┌───────────────────┐        ┌──────────────────────────────┐
│ 壳页面（GitHub Pages，被缓存）  │── 加密的牵线 ──▶│ 公共 MQTT（多个）  │◀─ 订阅 ─│ AnywhereService              │
│  ├ 配对 / 电脑列表 / 连接状态    │                └───────────────────┘        │  ├ 每台已配对手机一个牵线频道  │
│  ├ 通道（直连 / 慢速转发）      │◀═══ WebRTC 数据通道（DTLS，IPv6 优先）══════▶│  ├ node-datachannel           │
│  └ Service Worker：            │                ┌───────────────────┐        │  └ 桥接 ─▶ 127.0.0.1:3091     │
│     界面文件 / api/* 走通道      │                │ STUN（拿公网地址）  │        │      （现有远程访问入口，      │
│ 界面（iframe，文件取自电脑）     │                └───────────────────┘        │       设备令牌照常鉴权）       │
└──────────────────────────────┘     直连不通时：同一个 MQTT 上加密分片转发（慢）     └──────────────────────────────┘
```

**核心取舍**：电脑端只是一座「桥」——通道里的 WebSocket 和 HTTP 请求原样转给本机的远程访问入口（`RemoteService` 的 3091 监听器，socket 带 `cwRemote`，必须有设备令牌）。鉴权、设备列表、吊销、`/api/file`、附件上传全部复用，hub 不改。绝不桥接到主入口 3090（没配主令牌时回环免鉴权）。

## 1. 牵线

- **通道**：公共 MQTT over WSS，同时连多个（默认 broker.emqx.io、broker-cn.emqx.io、test.mosquitto.org、public.cloud.shiftr.io、broker.hivemq.com，以实测为准），同一条消息发到所有已连上的，接收端按消息 id 去重。列表可在设置的「更多选项」里改。nostr 只在实测证明 MQTT 在国内普遍不通时才加。
- **频道名与密钥**（HKDF-SHA256）：
  - 已配对设备：`K = sha256(设备令牌)`（电脑本来就只存这个哈希，不新增要保存的秘密）；频道 = `cw1/` + hex(HKDF(K, "topic")[0:16])，牵线密钥 = HKDF(K, "signal")。
  - 配对时：二维码里一次性的 16 字节配对密钥 P，频道和密钥同样由 P 派生（salt 不同）；电脑只在配对码有效的 10 分钟里订阅它。
- **消息**：`{v:1, t, s(会话 id), n(随机数), ts, from, …}` 用 AES-256-GCM 加密后发出；时间差超过 5 分钟、或 n 见过的一律丢掉（防重放）。类型：`hello`（手机来了，带手机随机数）→ `ack`（电脑在，带电脑随机数和电脑名）→ `offer` / `answer` / `cand`（WebRTC，候选逐个发）→ `relay`（改走慢速转发）→ `bye`。
- **电脑在不在**：手机发 `hello` 后 15 秒没有 `ack` = 「电脑没有回应」。电脑每个频道每分钟最多回 30 次 `hello`，多的丢掉。

## 2. 直连

- WebRTC 数据通道。电脑端用 **node-datachannel**（libdatachannel，MPL-2.0，Windows / macOS / Linux 预编译；网页版 `npm start` 和桌面版都在 server 进程里跑，不依赖 Electron 渲染进程）。手机端用浏览器自带的 `RTCPeerConnection`。
- STUN：stun.hitv.com、stun.cloudflare.com、stun.miwifi.com、stun.chat.bilibili.com（以实测为准，可在「更多选项」里改）。ICE 自己会优先选通的那对，IPv6 能通就走 IPv6。
- ICE 20 秒没连上 → 自动改走慢速转发（第 3 节）。连上后会话期间断开 → 先重新协商一次直连，不行再转发。
- 加密：DTLS。证书指纹在加密的牵线消息里交换，牵线服务器换不了 → 端到端。

## 3. 慢速转发（直连不通时的兜底）

- 默认走 test.mosquitto.org、public.cloud.shiftr.io、broker.hivemq.com（实测 5G 下全部到达；emqx 会限流，只用于牵线），同一帧同时发到几个，按序号去重。频道 `<频道>/r/<会话 id>/up|down`，密钥 = HKDF(K, salt = 手机随机数 ‖ 电脑随机数, "relay")，每条带序号，收端按序号重排、去重，丢了按窗口重传。
- **限制**（公共 broker 写明「不用于正式产品」，不能把它当带宽用）：每条 ≤ 12 KB 有效载荷、每秒 ≤ 20 条、单个 HTTP 响应 ≤ 2 MB；文件预览和附件上传在慢速模式下不可用（界面提示「慢速转发时不能预览 / 上传文件」）；界面文件只能用已缓存的，版本变了时只允许取首屏必需的文件（约 1.6 MB）。
- 手机上的连接状态写明「慢速转发（直连没打通）」。

## 4. 通道协议（直连和慢速转发共用，以后的中转也用它）

二进制帧：1 字节类型 + 4 字节流 id + 负载。

| 类型 | 方向 | 内容 |
| --- | --- | --- |
| `WS_OPEN` | 手机→电脑 | 设备令牌；电脑据此连 `ws://127.0.0.1:<远程端口>/ws?token=` |
| `WS_MSG` / `WS_CLOSE` | 双向 | WebSocket 文本帧原样 / 关闭 |
| `HTTP_REQ` / `HTTP_BODY` / `HTTP_END` | 手机→电脑 | 方法、路径、头（JSON）/ 分片 / 结束 |
| `HTTP_RES` / `HTTP_BODY` / `HTTP_END` | 电脑→手机 | 状态码、头 / 分片 / 结束 |
| `PING` / `PONG` | 双向 | 保活与测延迟 |

分片 16 KB，按 `bufferedAmount` 背压（> 1 MB 暂停）。一条通道可以并发多个流。

## 5. 电脑端：`server/src/remote/anywhere/`

- `AnywhereService`：远程访问开着且「在外面也能用」开着（`remote.anywhere`，远程访问打开时默认开）时启动：连 broker、为每台已配对设备订阅频道、处理牵线、建立直连 / 转发、把帧桥接到本机远程访问入口。
- 设备增删联动 `RemoteService`：配对成功 → 订阅新频道；吊销 → 退订并立刻关掉这台设备的所有桥接（现在的 `revoke()` 不踢已建立的连接，这里补上）。
- 状态 `remote.status` 增加 `anywhere: { on, brokers: {name, ok}[], sessions: {device, kind: 'p2p-v6'|'p2p-v4'|'relay', since}[], recent: 最近 20 次连接（时间、设备、结果、走的路、失败原因） }`。
- 本进程的网络代理设置（`net/proxy.ts`）对 broker 的 WSS 生效；直连（UDP）不走代理。
- 打包：node-datachannel 加进根 package.json 依赖和 `asarUnpack`；`smoke-packaged` 增加「模块能加载」的检查；mac 两个架构各自 CI 构建时装各自的预编译。

## 6. 手机端

- **壳**：`web/src/shell/`，Vite 第二个入口，产物 `web/dist-shell/`，GitHub Actions 在发版 tag 时部署到 GitHub Pages：`https://ypyik0669.github.io/claude-web/`（地址在设置「更多选项」里可改，给 fork / 镜像用）。壳很小，只有：电脑列表、配对、连接状态与报错、通道、Service Worker。不加载任何第三方脚本，CSP 只允许同源 + 牵线 broker 的 WSS。
- **界面放在 iframe 里**：壳连上电脑后，在全屏 iframe 里打开 `app/index.html`；iframe 同源，界面的 `ws/client.ts` 看到 `parent.__cwTunnel` 就用通道代替 WebSocket（同一个接口：send / onmessage / onopen / onclose），一条通道整个会话共用。
- **界面文件来自电脑**：壳经通道取电脑上的 `index.html` 和首屏文件，存进 Cache Storage（按电脑 + 版本分），之后按需取（编辑器这类大文件用到才取）。手机上的界面永远和电脑版本一致，每次发版不用把界面发布到别处。
- **Service Worker**：`app/` 下的文件从缓存给，缓存里没有就请壳经通道去取；`app/api/file`、`app/api/attachments` 这类请求同样转给壳走通道。界面代码不用知道自己在通道里。
- **构建改动**：Vite `base: './'`；界面里写死的 `/api/...`、`/manifest.webmanifest`、`/sw.js`、`/icon-*` 改成相对路径（一个 `appUrl()` 助手）。桌面版、局域网、`?win=` 多窗口都要回归验证。
- **存储**：设备令牌和电脑名存 IndexedDB；调用 `navigator.storage.persist()`；iOS 提示「添加到主屏幕」（不然 Safari 7 天不访问会清掉，要重新配对）。

## 7. 配对

1. 设置 → 手机与其它电脑 的二维码默认改成「在哪都能用」版：`<壳地址>#p=<base64url({v:1, ps:配对密钥, code:6 位配对码, pc:电脑名})>`。`#` 后面不会发给任何服务器。原来的局域网二维码在旁边保留（「只在局域网（不用联网）」）。
2. 手机扫码 → 打开壳 → 在配对频道里和电脑握手、建直连（在家时走局域网候选，很快）→ 经通道 `POST /api/pair {code, name}`（现有接口，次数限制照旧）→ 拿到设备令牌 → 存起来 → 改用设备频道 → 打开界面。
3. 以后在哪打开壳（或主屏幕图标），都会列出配对过的电脑，点一下连上。

## 8. 安全

- 二维码里的配对密钥一次性、10 分钟有效、不经过任何服务器。
- 牵线服务器只看到哈希过的频道名、密文的大小和时间、双方 IP；STUN 服务器看到双方 IP。写进设置页的说明。
- 设备令牌只在加密通道里传；电脑端照旧用它鉴权，吊销立刻生效（退订 + 断开）。
- `sha256(令牌)` 现在也是通道密钥的来源：诊断包的 `maskSecrets` 要把 `tokenHash` 打码（现在没有）。
- **剩下的风险**：壳页面托管在项目的 GitHub Pages。GitHub 账号被盗、壳被换掉，就能偷到手机上的设备令牌。对策：壳尽量小、不引第三方脚本、Service Worker 缓存后只在新版本时更新；风险写进 README。

## 9. 不让电脑睡眠

- 设置「远程访问开着时不让电脑睡眠」（`remote.keepAwake`，远程访问打开时默认开）。桌面版用 Electron `powerSaveBlocker.start('prevent-app-suspension')`，条件不满足时 `stop`。server 设置变化时通知桌面壳（现有 `parentPort` 通道）。
- 屏幕照样会关；笔记本合盖照样会睡（说明里写明）。网页版没有这个能力，只给一句提示：去系统电源设置里关掉睡眠。

## 10. 界面与文案

- 设置 → 手机与其它电脑：
  - 「在外面也能用」开关 + 一行状态：「可以从外面连」/「连不上牵线服务器，检查网络」。
  - 二维码默认「在哪都能用」，旁边一个切换「只在局域网」。
  - 设备列表每行加最近一次：「直连 · IPv6 · 3 分钟前」/「慢速转发」/「没连上：…」。
  - 「不让电脑睡眠」开关。
  - 「更多选项」：牵线服务器列表、STUN 列表、壳页面地址、最近 20 次连接。
- 手机壳的报错（都配原文，走 `errors/explain.ts` 同一套）：
  - 「电脑没有回应：电脑可能关机、睡眠，或 Claude Web 没在运行。」
  - 「连不上牵线服务器：这个网络可能拦了，换个网络试试。」
  - 「直连没打通，已改用慢速转发：文字能用，文件预览和上传不能用。」
  - 慢速转发也不通 →「连不上。可以先用 IM 机器人（设置 → IM 机器人）。」
- 默认界面不出现「MQTT / WebRTC / STUN / ICE」，这些只在「更多选项」和 tooltip 里。

## 11. 以后的中转

- 通道协议（第 4 节）和传输无关：`Link { kind: 'p2p' | 'mqtt' | 'relay', send(frame), onframe, close }`。以后有了中转服务器，加一个 `relay` 实现（电脑和手机都主动 WSS 连中转，按频道转发密文），排在直连之后、MQTT 慢速转发之前。
- 二维码 `v:1` 的 JSON 可以加 `relay` 字段；没有这个字段的旧配对照样能用。

## 实测（先于完整版）

探测版（会话 scratchpad 里的 `p2p-probe`，不进仓库）：手机在 Wi-Fi 下打开电脑上的测试页，切到流量后测 STUN、NAT 类型、IPv6、各 broker、nostr、网页托管、和电脑真直连（不限 / 只交换 IPv4 / 只交换 IPv6）、MQTT 慢速转发的丢包和延迟。

**第一轮结果（2026-10-01，吉隆坡，iPhone Chrome；电脑在家宽）**：

| | 家里 Wi-Fi（对照） | Yes 5G |
| --- | --- | --- |
| 手机 IPv6 | 有 | **没有** |
| 手机 IPv4 NAT | 对称型（端口顺序递增） | 对称型（端口顺序递增） |
| 牵线（5 个 MQTT） | 4 通（mosquitto 不通） | 5 通 |
| nostr | 3/6 | 3/6 |
| 网页托管 | 全部能打开（github.io ~1.1 s） | 全部能打开 |
| 直连 | 0.5 s 连上，5 ms，~9 MB/s（局域网候选） | **三次都失败**（两边 IPv4 都是对称型，手机没有 IPv6） |
| 慢速转发 | 40/40，中位 457 ms | mosquitto / shiftr / hivemq 20/20 + 突发 30/30，中位 420–470 ms；emqx / emqx-cn 只收回约一半（突发封顶 10 条，像是限流） |

结论：门槛达到。手机流量 + 对称型 NAT + 没有 IPv6 时直连打不通，**慢速转发是这类网络唯一能用的路**，延迟约 0.5 s，聊天够用。据此：**慢速转发默认用 mosquitto、shiftr、hivemq（多条并发、按到达去重），emqx 两个只用于牵线**；一条消息丢了靠序号重传。国内网络的情况还没测，要找国内用户用同一个探测版再测。

**做完整版的门槛**：手机流量下至少 2 个 broker 通；并且「直连成功」或「慢速转发 40 条收回 ≥ 36」至少一个成立。测出来的 broker / STUN 列表就是默认列表。达不到就回到方案选择（自建中转提前）。

## 测试

- 单测：帧编解码（分片、背压）、牵线信封（篡改、重放、时间差、去重）、频道与密钥派生（对照固定向量）、慢速转发的序号 / 重排 / 重传、SW 请求路由（纯函数）、`appUrl()`、`maskSecrets` 打码 `tokenHash`。
- 端到端（新 phase）：本机起一个最小 MQTT broker（测试用）+ server + 一个用 node-datachannel 扮演手机的客户端：配对、经通道发 `sessions.list`、`/api/file`（含 Range）、附件上传、吊销后立刻断开、强制 ICE 失败走慢速转发、慢速转发下文件预览被拒。
- ui-smoke：设置页新区块；壳页面在 Electron 里用假通道打开界面 iframe。
- 真机：照探测版的矩阵（三家运营商 × 4G/5G × 家宽，iOS Safari / Android Chrome / 微信内置浏览器）。

## 风险

- 公共 broker 和国内 STUN 都不是给我们用的：可能限流、下线、被封。多个并用 + 可在设置里改 + 以后的中转兜底。
- 打洞失败率在只有 IPv4 的网络上会很高；IPv6 的收益要靠实测确认。
- github.io 在国内时好时坏：只影响第一次打开和壳更新；以后加 Cloudflare Pages / unpkg 镜像。
- node-datachannel 是原生模块：打包、mac 两个架构、Electron utilityProcess 加载都要验证（计划第一步）。
- 微信内置浏览器的 WebRTC 支持没有官方说明，运行时检测，不支持时提示用系统浏览器打开。
