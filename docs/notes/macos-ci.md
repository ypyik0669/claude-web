  - **node-datachannel 自己编**（2026-11-27，用户选的方案）：npm 上的 darwin 预编译（0.33.0–0.33.6 都一样）标的 minos 是 arm64 14.0、x64 26.0——上游的 `build-mac-*.yml` 没设部署目标，x64 是在 `macos-latest`（macOS 26 的 arm 机）上交叉编的。**minos 本身不拦 dlopen**（CI 上 macOS 15 的 Intel 机加载 26.0 的那份照样 `rtc ok`），拦的是导入符号：解析符号表、对 libc++ 的 `__configuration/availability.h`——两份都导入 `basic_filebuf` / `basic_stringbuf` / `istringstream` 的显式实例化（`ADDITIONAL_IOSTREAM_EXPLICIT_INSTANTIATIONS_1`，**macOS 12.3**），x64 还导入 `__cxa_init_primary_exception` 和 `exception_ptr::__from_native_exception_pointer`（`INIT_PRIMARY_EXCEPTION`，LLVM 18，**macOS 15.0**）。所以实际门槛 arm64 12.3、x64 15.0，以下加载失败、手机只能走转发（`rtc.ts` 按需加载，不影响启动）。现在 `release.yml` 的 mac job 在打包前跑 `scripts/mac/build-datachannel.sh`：OpenSSL（钉 `openssl-3.5.9`，静态）和 node-datachannel（装着的同一版本，`v<ver>` tag，cmake-js）都在 `MACOSX_DEPLOYMENT_TARGET=12.0` 下编，链接日志里出现「built for newer macOS version」就失败（静态库里混进新目标时最终产物照样标 12.0），产物换进 `node_modules/@node-datachannel/darwin-<arch>/`；`actions/cache` 按 平台 + 版本 + 脚本哈希 缓存 `vendor/datachannel/`（第一次编 arm64 约 4 分钟、x64 约 8 分钟）。**缓存按 ref 隔离**：tag 上的 run 只能用 main 存的缓存，自己存的下一个 tag 用不上——所以升级 node-datachannel 或改了这个脚本后，先在 main 上 `gh workflow run release.yml --ref main` 跑一次（只打包不发布），缓存存到 main 上，之后发版才命中。打包后 `scripts/mac/check-min-os.mjs` 查整个 .app 的每个 Mach-O 的 minos ≤ 12.0，解析在 `scripts/mac/macho.mjs`（测试 `server/src/app/mac-min-os.test.ts`）。第一次跑查出的 30 个 Mach-O 里 Electron 43 框架、Magpie、sidecar、node-pty、sharp 都 ≤ 12.0，只有两个超：官方 `claude`（13.0，允许名单）和 **CLIProxyAPI v8.0.45（标 15.0）**——它是 Go 1.26.10 + `CGO_ENABLED=1`，在 macOS 15 的机器上用系统 clang 链接，带上了构建机的版本；导入的 169 个符号全是 Go 运行时那套 + cgo 的 DNS（`res_9_*`），最新的 `SecTrustCopyCertificateChain` 是 12.0，所以在 12 上能跑，进了允许名单。**Go 1.26 是最后一个支持 macOS 12 的 Go**（Go 1.27 要 13），所以检查带 `--go-max 1.26`：读 Go 二进制的 build info（`\xff Go buildinf:`），Go 1.27 及以后的不管在不在允许名单都判失败——以后升级 CLIProxyAPI 撞上它时，要么钉在 Go 1.26 编的版本，要么在托管程序页上说明 macOS 12 用不了。**升级 node-datachannel 时**看上游构建方式变没变（CMakeLists 的 FetchContent / OpenSSL 选项）。
