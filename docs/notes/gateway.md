- **透传是命根子**（Claude Code → 网关 → 用户的中转，中转查 UA / 系统提示 / entrypoint）：上游用 `node:http(s)` 而**不是 fetch**（undici 会自己加 `accept-encoding` / `sec-fetch-mode` / `accept-language` 并自动解压）。请求头按 `rawHeaders` 的原顺序原大小写转发，只去掉 hop-by-hop（含 `Connection` 里列出的字段）、cookie、`x-cw-*`；成员密钥**原位**替换第一个凭据头的值（客户端用 `x-api-key` 就发 `x-api-key`，用 Bearer 就发 Bearer），多余的凭据头删掉。`accept-encoding` 里的 `zstd` 只在本机 zlib 能解（`createZstdDecompress`）时保留，否则嗅 usage 会读到乱码。改模型只替换**顶层** `model` 字段的字节（`replaceTopLevelString`，小 JSON 扫描器），模型不变时请求体原样。响应状态 / 头 / 字节原样回，usage 从解压副本里嗅（`UsageSniffer`）。网关档案给 Claude 的 env 与 anthropic 档案相同（`CLAUDE_WEB_PLAIN_UA` + `CLAUDE_CODE_ENTRYPOINT=cli`），否则经网关透传到中转也会被指纹拒。
- **故障转移**：拿到 2xx 响应头后还要等第一块 body 才向客户端写头（**流式**首字节 60s，`FIRST_BYTE_MS`；非流式要等整段生成完，给 10 分钟 `NONSTREAM_MS`），所以「200 后卡住」也能切换；写了头就不再切换，上游半路断开 → 透传直接断，转换流补一个协议内的 error 事件。429 / 402 / 额度文本（`QUOTA_RE`，含中文「额度 / 余额」）→ 按 `retry-after` / `anthropic-ratelimit-*-reset`（取 remaining=0 的那个）/ `x-ratelimit-reset-*`（`6m0s` 这种时长）冷却，没有就 60s×2^n 上限 30 分钟；5xx / 529 / 网络 / 超时 → 冷却 15s；401/403 → 停用到用户点「恢复」或改组；其它 4xx 原样回、不切换。全员冷却 → 429/503 带 `retry-after`；原样回的上游错误保留 `retry-after` / `request-id` / `*-ratelimit-*` 头。**并发**：每次尝试记 `sentAt`，成员在它发出之后已被别的请求打入冷却，就只更新错误文本、不加退避次数，冷却也只按上游响应头给的时长延长（不拿自己的退避猜测再抬一档）（否则 N 个并发 429 一次把退避推到 30 分钟上限）；成功也只在 `sentAt` 晚于最近一次失败时才清冷却。`count_tokens` 的成败不改成员状态，失败时回估算。**客户端断开**：`waitDrain` 在 signal 已经 abort / socket 已毁时立即返回（abort 事件不会再触发，旧实现会永远挂住），账本记 499 `ok:false`，成员不冷却。成功响应带 `x-cw-gateway-member`（URI 编码的档案名）和 `x-cw-gateway-switches`。
- **会话接入**：`ProviderType` 加 `gateway`（`Provider.gatewayGroupId`）；`ProviderService.forSession()` 通过 `gatewayEndpoint` 钩子把 baseUrl / apiKey 填成 `http://127.0.0.1:<port>/gateway/<组>` + 网关密钥（端口在 listen 后写进 `gateway.port`，桌面版每次都变，所以只在开会话时算）。`providerEnv(p, agent)`：Claude 同 anthropic；Codex → `OPENAI_*` + `CW_GATEWAY_KEY`；ACP agent → `GOOGLE_GEMINI_BASE_URL` + `GEMINI_API_KEY` + OpenAI 那两个。**账号登录会盖过 env**，所以 `providers.agentLaunch()`（`RunnerPool.open` 用）另外：Codex 在 `app-server` 前插 `-c model_providers.cwgw.{name,base_url,env_key="CW_GATEWAY_KEY",wire_api="responses"}` + `-c model_provider="cwgw"`，档案有默认模型时再加 `-c model="…"`（`gateway/agents.ts`，不碰 `~/.codex/config.toml`），且 `codex-driver` 的「模型不在 model/list 就换默认」对网关会话不生效（网关背后的模型不在 ChatGPT 列表里）；Gemini CLI 的缓存 Google 登录（用户 settings 的 `security.auth.selectedType`）优先于 `GEMINI_API_KEY`，而 ACP `authenticate` 会改用户 settings 还清掉缓存凭据，所以改用 `GEMINI_CLI_SYSTEM_SETTINGS_PATH` 指向一份「系统设置副本 + `selectedType: gemini-api-key`」（系统设置覆盖用户设置），写在 `<dataDir>/gateway/`（原子写：临时文件 + rename，Windows EPERM/EBUSY 重试），**只对 gemini 这个 kind**；Qwen Code 等只注入 env，OAuth 登录下可能不走网关。网关 401 且来的不是 `cwg-` 密钥时错误里提示「agent 没有用网关密钥」。组里有 `runtime:'claude'` 的 Anthropic 成员时，网关档案默认也用官方二进制（`endpoint().runtime`，档案显式设置优先）；「测试」按钮的请求不带 Claude Code 指纹，结果里有说明。
- **协议坑**：OpenAI 的 `prompt_tokens` 含缓存，IR（同 Anthropic）分开记；o 系列 / gpt-5 只收 `max_completion_tokens`；Chat 流要 `stream_options.include_usage` 才有 usage；Chat 的 `tool` 消息只收文本（`string | text part[]`），tool_result 里的图片放到紧随的 `user` 消息（`[tool result image for <id>]` + image_url）；Claude 新模型不收 temperature + top_p 同时出现，转 Anthropic 时只留 temperature；Codex 的 `custom` 工具（apply_patch 自由格式）转成只有 `input` 字符串参数的函数，回程再变回 `custom_tool_call`；Gemini 的 `parameters` 只收 OpenAPI 子集（`sanitizeSchema` 去 `$schema/additionalProperties/const…`，`["string","null"]` → `nullable`），genai SDK 发的 `OBJECT/STRING` 要转小写；Gemini 3 对历史里没有 `thoughtSignature` 的 functionCall 报 400，转换时补 `skip_thought_signature_validator`（此值未在官方文档核实）；Gemini 的调用 id 可选，按名字 + 顺序配对 functionResponse。

## 内嵌网关（阶段 A，2026-10-19）

- 账号在 `server/src/upstreams/`：`AccountStore` 只管加密 / 去重 / 级联删除，`UpstreamService` 管池子、策略、会话粘性和目标解析，`ClaudeAdapter` 管凭据探测和 OAuth 刷新。
- 网关成员是 `p:` / `a:` / `u:` 三选一（`gateway/types.ts` 的 `memberKey`）；状态表 `MemberStates` 用同一个 key，旧的裸 provider id 自动当成 `p:`。账号成员永远走 IR 翻译（Bearer + `anthropic-beta: oauth-2025-04-20` + Claude Code 系统前缀），不字节透传——订阅登录需要 Claude Code 的请求形状。
- 根路径：`/v1/...`、`/<组>/v1/...`；旧 `/gateway/<组>/...` 保留（拆分子代理路由和缓存垫片也在这下面）。根路径下多个组时用 `组名/模型` 指定；`?key=` 默认关闭（`gateway.allowQueryKey`）。
- 密钥：`cwg-` 明文只出现一次，落盘是 `sha256(salt + key)`；旧单密钥迁移成 `key_default`（保留 `secret`，所以「显示密钥」还能用），重新生成时原地换哈希。密钥组空 `routeGroupIds` = 全部（迁移来的默认组）；IP 白名单、模型 glob、RPM / 并发 / 每日 token 预算都在 `serveRequest` 入口统一裁决。
- 局域网是独立 `GatewayListener`，只认 `/v1`、`/v1beta`、`/healthz`；密钥组必须 `allowLan`，非回环来源必须命中白名单；监听地址只接受私网 IP / 127.0.0.1 / 0.0.0.0（后者要二次确认）。CORS 默认不发头，列出的 origin 才回显。
- 审计只写白名单 12 个字段，1 秒一批、每批最多 200 行，按 `gatewayAudit` 轮转；`gateway.log` 事件推给前端。准入拒绝（401 / 403 / 429 / 413 / 400）也各写一行，`member` 为空。
- 会话粘性在 `upstreams/affinity.ts`：内存、TTL 默认 60 分钟；会话键依次取 `prompt_cache_key` / `session_id` / `conversation_id` / `x-claude-code-session-id` / `metadata.user_id`；账号失败（429 / 401 / 5xx）时解除该账号的所有绑定。池子的 `modelMap` 结果放在 `GatewayTarget.model`，优先于网关组的映射。
- 每日预算在请求入口检查、响应后记账，所以并发突发可能短暂超过 token 上限（顺序请求严格 429）；`dailyCostUsd` 只统计不生效（网关不知道价格）。
- `count_tokens` 只对同协议成员转发；账号成员（强制翻译）和跨协议入口用本地估算，响应头 `x-cw-estimated: 1`，不会变成一次真实生成。
- 局域网配置里只有 `enabled` / `bind` / `port` 变化才重启监听器；白名单 / CORS / 体积上限按请求读取，改它们不会换端口。
- 现有的 `claude-account` 供应商档案也能当网关成员（`ProviderService.member` 不再排除它）：`outboundOf` 当 Anthropic，但同样强制翻译（Bearer + oauth beta + 系统前缀），地址走档案的 baseUrl 或 api.anthropic.com。
- 单账号代理：`UpstreamAccount.proxy`（http(s) / socks4/5）解密后放进 `GatewayTarget.proxy`，`sendUpstream` 用 `agentFor` 覆盖进程级代理；`maxConcurrent` 由 `UpstreamService.acquire/release` 在请求期间占位，满了就跳到下一个成员。池里没有健康账号时会退回最早恢复的那个，并在回答头里带 `x-cw-degraded: 1`。
- 测试：`upstreams/{store,claude,service,affinity,keys,routing}.test.ts`、`gateway/audit.test.ts`，以及 `gateway/service.test.ts` 里的根路径 / 密钥组 / 限速 / LAN / 账号成员用例；端到端 `server/ws-phase30.mjs`（假 Anthropic 上游，20 项）。

## 内嵌网关（阶段 B/C：Gemini / WorkBuddy sidecar 与任务中心，2026-10-19）

- **边界**：Claude 订阅仍在主进程（`ClaudeAdapter`）；Gemini 网页和 WorkBuddy 各自跑一个 MIT 单文件 sidecar 二进制。主进程只通过 sidecar 的 HTTP API 说话：账号池、cookie / OAuth 续期、家族内部轮换都是 sidecar 的事；跨家族故障转移仍归网关。
- **清单**：`upstreams/sidecars.json` 固定版本 + 每平台 `url / sha256 / size / entry / archive`。`SidecarManager.install` 下载到临时目录、校验大小和 SHA256、解压（zip / tar.gz）、把 entry 提到包根、原子 rename 到 `dataDir()/sidecars/<id>/<version>/`；失败不替换旧版本。Windows 上 PATH 里的 `tar` 是 Git 的 GNU tar（`C:\…` 会被当成远程主机，也不认 zip），所以 zip 改名成 `.zip` 后交给 PowerShell `Expand-Archive`，tar.gz 用 `System32\tar.exe`；macOS / Linux 用 `tar` / `unzip`。开发 / 端到端用 `CW_SIDECAR_<ID>_BIN`（可执行文件本身）或 `CW_SIDECAR_<ID>_CMD`（JSON 数组，`["node.exe","fake.mjs"]`，用来跑假 sidecar）。安装包里带的版本在 `CLAUDE_WEB_SIDECARS`（Electron 传 `resources/sidecars`），`binary()` 先找它再找下载目录。
- **启动**：随机空闲端口；管理 token / API key 每次进程随机生成，只通过环境变量传（Gemini 的 `ADMIN_TOKEN` / `API_KEY`），不进 argv；WorkBuddy 的配置写 `<dataDir>/sidecars/workbuddy/wb2api.json`，0600，`schedule.*_enabled` 全关（调度归我们）。spawn 带 `windowsHide: true`。就绪前 500ms 轮询健康检查；就绪后每 30 秒一次，连续 3 次失败就杀掉进重启路径。进程退出按 1s / 2s / 4s … 上限 60s 退避，活过一分钟重置。日志 `<dataDir>/logs/<id>.log`，5MB 轮转一份。
- **健康**：Gemini 的 `/admin/api/config` 要管理 token；WorkBuddy 的 `/healthz` 在账号池为空时回 **503**（`healthy:0,total:0`，进程是活的），适配器把 200 / 503 都当作就绪，否则空池子永远起不来。就绪后每 30 秒复查，连续 3 次失败杀进程进重启路径。
- **账号镜像**：Gemini / WorkBuddy 账号先写 sidecar，再写本地行，`UpstreamAccount.sidecar = {id, remoteId, syncedAt}`。sidecar 自己扫码 / OAuth 登录出来的账号用 `upstreams.sync`（`AccountStore.addManaged`，本地没有明文凭据，只有链接）拉进列表；改名 / 启停 / 换凭据都先问 sidecar（换凭据 = 新加一条再删旧的）；删除先删 sidecar 账号，失败也继续删本地行。Gemini 的凭据统一成 `{kind:'cookie', cookie}`；WorkBuddy 接受 cockpit JSON（数组或单个 `{uid, accessToken, refreshToken}`），`normalizeCredential` 也认这个形状用于去重。
- **网关目标**：一个家族一个 `sidecar:<kind>` 目标（`type:'openai'`，baseUrl 指回环 sidecar 的 `/v1`），不是每个账号一个——家族内部选谁由 sidecar 决定，网关只在家族之间切换。目标不套账号代理（连的是回环）。sidecar 报告的模型列表缓存在 `UpstreamService.familyModels`，`/v1/models` 把账号成员和池子的家族模型一起列出来。
- **任务中心**（`upstreams/tasks.ts`）：类型 `checkin / keepalive / growth / travel / lottery / activity / quota-refresh / account-check`；家族矩阵在 `UpstreamService.familyTasks`（Gemini 只有保活 / 检查 / 额度，WorkBuddy 全有，Claude 只有检查 / 额度），不能执行的任务不写运行记录。`tasks.upsert` 校验目标和 cron / 间隔（5 分钟～7 天）；tick 30 秒，同一任务不并发；幂等键 `task:account:slot`（签到 / 旅行 / 抽奖按本地日期，其它按计划时刻），手动执行用 `manual:<now>` 绕过去重；错过 3 分钟以上算补跑，超过 7 天直接丢弃并重排；`maintenanceRuns` 只留最近 500 条。运行结果回写账号额度 / 健康；每次运行打一行服务端日志，有账号失败时再发 `notice`（前端 toast，焦点不在时走系统通知），前端看运行历史。
- **前端（2026-10-20 为普通用户简化）**：默认只显示 **概览 / 账号 / 任务**；分组与路由、密钥、日志、局域网设置收进「高级设置」（`GatewayPage` 的 `advanced`，`isAdvancedTab` 自动展开，收起时若停在高级页会回到概览）。添加账号向导是三个大按钮（Claude / Gemini / WorkBuddy）+ 一个「添加」，不再点两次确认（2026-10-21 用户要求去掉了「我了解」风险勾选，嫌多此一举）；WorkBuddy 的「扫码登录 / 粘贴 JSON」是分段控件（`ui/Segmented`，弹窗里的 `<label>` 被全局样式撑成块级，单选框排不齐），底部是标准 `.modal-actions`。概览只有开关、地址 + 一键复制密钥、三个数字、账号入口和连接状态；「侧车」这个词不再出现在界面上，统一叫「组件」。任务页顶部是三个常用预设（每天签到 / 每 6 小时保活 / 每天刷新额度），一次给所有同类账号建任务；自定义编辑器保留在「自定义任务」后面。账号池只有高级模式下显示；**新装环境添加的第一个账号会自动进一个「默认」网关组**（已有自己的组就不动），所以根路径 `/v1` 不用建组、建池、建密钥就能直接用。
- **测试**：`upstreams/{sidecar,adapters,service-sidecar,tasks}.test.ts`（安装哈希、崩溃重启、健康监控、两个适配器的假 HTTP、sidecar 账号镜像、调度 / 幂等 / 补跑 / 上限）；端到端 `server/ws-phase31.mjs`（两个假 sidecar：网关经 Gemini 回答、WorkBuddy 扫码 + 同步 + cockpit 导入、任务运行、启停、删除，22 项）。

## Gemini 账号：弹窗登录 + 粘贴检查（2026-10-20，用户反馈手抄 cookie 总失败）

- **为什么手抄会失败**：① 只复制 DevTools → Application 里 gemini.google.com 那一栏，SID / HSID / SSID / APISID / SAPISID 挂在 `.google.com` 上，组件回 400「cookie 里没有 SAPISID」；② 复制完浏览器接着用，`__Secure-1PSIDTS` 被浏览器轮换，组件里的副本马上「已过期」（日志里只看到 `[rotate] 刷新了 __Secure-1PSIDCC, SIDCC`，从没刷新过 1PSIDTS）。
- **桌面版登录走本机 Chrome（不是应用内窗口），分两步、登录时不许有任何调试通道**：Google 拒绝内嵌浏览器的登录（Electron 里点登录直接「Couldn't sign you in / This browser or app may not be secure」，GUI 那个方案实测就被拦了）；真 Chrome 带 `--remote-debugging-port` 也一样被拦（2026-10-20 实测，端口开着登录页直接拒绝）。所以 `desktop/src/gemini-login.ts` 的流程是：
  1. **登录窗口**：spawn 本机 Chrome（没有就 Edge，`browserCandidates` 按平台/环境变量找），只有 `--user-data-dir=<userData>/gemini-browser/gemini-<hex>`（每个 Google 账号一份独立 profile，不跟用户自己的 Chrome 共用，所以不会被别处轮换掉）+ `--no-first-run` + `--no-default-browser-check` + 窗口大小，**不带任何 `--remote-debugging-*`**，第一次去 `accounts.google.com/ServiceLogin?continue=…/app`，重新登录直接开 `/app`。等用户自己关窗（最长 10 分钟）。
  2. **静默读取**：用户关窗后，用同 profile 起一个 `--headless=new` + `--remote-debugging-pipe` 的 Chrome，只开 `about:blank`、**不访问任何 Google 页面**，通过管道 CDP 读 `Storage.getCookies`，读到必需六个 cookie 就返回；读完 `Browser.close`。headless 的 UA 带 `HeadlessChrome/`，返回前替换成 `Chrome/` 再交给组件。
- **Chrome 的 DBSC 会把登录弄成「30 分钟就死」**（2026-10-20 实测）：Chrome 155 登录 Google 时下发 Device Bound Session Credentials，把会话绑定到本机设备密钥；组件（Go）没法生成签名 JWT，`POST /RotateCookies` 的哨兵刷新被 401，`__Secure-1PSIDTS`（约 30 分钟过期）永远刷不到，之后 `/app` 页面就没有 `SNlM0e`，表现为 `cookie 池里 1 个账号都不可用（no SNlM0e in page）`。诊断特征：日志里 rotate 只刷 `SIDCC / 1PSIDCC / 3PSIDCC`（匿名也会刷），从不刷 `1PSIDTS`；profile 的 `Default/Network/Device Bound Sessions` 非空。修法：登录窗口加 `--disable-features=DeviceBoundSessions`（Chromium 的 feature 名，见 `net/base/features.cc` 的 `kDeviceBoundSessions`），Google 就不下发绑定；**旧 profile 已有绑定，必须删账号（连带删 profile）后重新登录**，只在同一 profile 上「重新登录」不解决问题。组件 `rotate.go` 的注释也给了另一条路：用 Firefox 登录再导出（Firefox 没有 DBSC）。
- **Claude Code 一轮 160 KB 的构成与提速（2026-10-21 实测）**：组件 `requests` 表记录 `prompt_chars` / `ttfb_ms` / `total_ms`。实测一句「你好」= 145–165 KB、35–40K token，`ttfb_ms` 20–28 秒、`total_ms` 62–137 秒而输出只有 16–34 token。原因：Claude Code 的系统提示 + 工具 schema（组件用 `json.MarshalIndent` 两空格缩进序列化，仅工具定义就 ~105 KB）超过组件 `max_prompt_bytes=128000`，被转成 `message.txt` 附件先上传、Gemini 读完才回答。三条杠杆：①**精简工具集**——`GatewayService.endpoint()` 对「全 sidecar 成员的组」返回 `leanTools: true`，`session-runner` 用 `LEAN_TOOLS`（Read/Edit/Write/Bash/Grep/Glob/TodoWrite）代替全套工具，prompt 能降一大截、避开附件路径；②**多轮续接**（组件 `multi_turn`）——后续轮次只发增量；③**放宽/关闭 `max_prompt_bytes`**——0 = 从不转附件，但上游可能从尾部静默截断。三项都在「出口」面板的防封设置里。
- **sidecar 的首字节超时要放宽**（2026-10-20 实测 504）：组件遇到超过 128 KB 的 prompt 会先把它转成附件上传（日志 `[context] prompt … 已转成附件 message.txt`），加上内部 3 次重试，首字节经常超过 60 秒；网关默认 `FIRST_BYTE_MS = 60s` 会把它当成上游卡死报 504。现在 `sidecar:` 成员的流式首字节超时是 `SIDECAR_FIRST_BYTE_MS = 180s`，其它上游不变。
- **管道细节**：spawn 时 `stdio: ['ignore','ignore','ignore','pipe','pipe']`，fd3 我们写、fd4 Chrome 读，消息以 NUL `\0` 分帧（不是换行）；写端必须监听 `error`（EPIPE 否则会带崩主进程）。`Cdp` 只发浏览器级命令（`Storage.getCookies` / `Browser.getVersion` / `Browser.close`），**不 attach 页面**（attach + Runtime.enable 是 Google 检测的东西）。完成判据 `loginReady`：必需六个 cookie 都有值；`googleCookies` 取 `.google.com` + `gemini.google.com` 的（更具体的域优先同名）。关窗没登录成 = 读不到 = null；10 分钟没关窗 = 超时返回 null。同时只开一个（`BUSY`）。
- **实测**（2026-10-20）：登录窗口命令行里无任何 `remote-debugging` 参数（含子进程）；关窗后 headless 读取实例正常启动（约 1 秒）、空档案返回 null；取消路径 24 秒内干净返回、无残留进程。
- **前端**：`features/gateway/gemini-login.ts` 的 `signInGemini` = 登录 → `upstreams.add`（或 `upstreams.update {credential}`，id 不变）→ `upstreams.probe`（sidecar 账号添加时服务端不探测，不探测就要等第一次用才知道死没死）。账号 id → profile 记在 meta `gateway.geminiLogins`（值仍是 `persist:gemini-<hex>`，目录名去掉前缀）；删账号时 `forgetGeminiLogin` 清映射并删掉那份 Chrome profile（顺带清掉旧版留下的 Electron 分区）。账号行在 Gemini 非 ok，或被组件自动停用（`autoDisabledAt`）时出「重新登录」；重新登录写回凭据时一并带 `enabled: true`（`upstreams.update` 换凭据 = 组件里新加一条再删旧的，`enabled` 要另外再发给新那条）。
- **模型菜单要看得到池模型**：`gateway.status()` 现在带 `poolModels`，key 是成员 `a:<accountId>`（单个账号成员——默认组就是这种）或 `u:<upstreamGroupId>`（账号池成员），值是 `familyModels(kind)`；前端 `models/menu.ts` 的 `gatewayModels()` 用同样的 key 并进网关档案的模型列表。最初只认 `upstreamGroupId`，用户默认组全是账号成员，菜单一个都没有。之前只有外部客户端的 `/v1/models` 能看到 Gemini 模型。
- **模型列表随登录变，要会过期**：组件没可用账号时只报 2 个匿名模型（`gemini-3.5-flash-lite` / `gemini-3.6-flash`），登录后才是订阅的完整列表（Pro 15 个，含 `gemini-4-argon`）。所以 `familyModels()` 有 5 分钟 TTL（`MODELS_TTL_MS`，过期就后台重拉，30 秒内不重复拉，拉完 `emit('changed')`）；换凭据（重新登录）后立刻 `rememberModels`；Gemini 卡片有「刷新模型」（`upstreams.models.refresh`）。前端 `models/data.ts` 监听 `upstreams.changed` 重新拉 status。
- **网关组自动是供应商档案**（2026-10-21，用户嫌「还要再去供应商里加一条」多此一举）：`GatewayService.syncProfiles()` 在启动、`upsertGroup` / `removeGroup`、`UpstreamService` 把账号放进默认组（`onGatewayGroups` 回调）时，给每个组建一条 `type:'gateway'` 档案（名字 = 组名）；组没了就删掉它的档案。用户在设置里删掉某个组的档案 → `providers.remove` 把组 id 记进 `gateway.dismissedProfiles`，以后不再自动建；手动再加回来时从这个名单里去掉。前端在 `gateway.changed` 时重拉供应商列表。
- **模型菜单里的一句说明**：网关档案的模型是原始 id，`menu.ts` 的 `gatewayModelHint()` 按名字给一行（`-thinking` → 思考 20–40 秒，`flash-lite` → 最快，`flash` → 快 · 写代码推荐，`argon` → 旗舰 · 最慢，`pro` → 更强 · 较慢，image / music / video → 生成类）。只对 `type === 'gateway'` 的档案，其它档案的 hint 仍是原始 id。
- **精简工具集反而更大（2026-10-22 用户报告：新开的对话发一句就弹「超过 170 KB」）**：`tools: LEAN_TOOLS` 收窄内置工具时，引擎也没了工具搜索（ToolSearch / ExecuteExtraTool），于是**所有 MCP 工具的 schema 全部内联**：账号的 claude.ai 连接器、用户 settings 里的服务器、我们自己的 claude-web-memory / web / sessions / preview。实测（ccb、本机真实配置、本地假接口抓第一轮 body）：全套工具 126 KB（26 个工具，其余延迟加载），旧精简 183 KB（73 个），现在的精简 62 KB（7 个）。现在 `leanTools` 和「只聊天」一样：`strictMcpConfig: true` + `mcpServers: {}`、不加插件、不加验证 / 子代理那几段系统提示（没有对应的工具）。代价：Gemini 网页 / WorkBuddy 组的对话没有 MCP 工具（联网、共享记忆）。测试 `session-runner.test.ts`「a sidecar-only gateway」。
- **对话超过 128 KB 提醒一次**（toast 说出是哪个对话、哪个成员：`promptHeavy` 带 `via`，2026-10-22 起；之前总写「Gemini 网页」，WorkBuddy 组也这么说）：组件每轮重发整段 prompt、没有提示缓存，过了 `max_prompt_bytes` 就转附件、过了约 163 KB 上游还会截断末尾。网关 `attempt()` 对 `sidecar:` 成员看出站 body 字节数，超过 `HEAVY_PROMPT_BYTES = 128_000` 就按 `x-claude-code-session-id` 发一次 `promptHeavy` → ws `gateway.promptHeavy` → 前端 toast 建议 `/compact`；同一对话只提醒一次，回到线下（压缩过）就重新武装。
- **出口（住宅 IP）**：组件的代理池就是出口池（`/admin/api/proxies`，每个出口有 fail_count + 熔断冷却）。claude-web 在「连接方式 → Gemini 网页」卡片里管理（`ExitsPanel.tsx`，走 `upstreams.proxies.*`）。账号 ↔ 出口由组件自动绑定并复用（`accounts.proxy_id`，`bindAccountProxy`）；手动指定出口走 `upstreams.update { proxyId }`，实现是直接写组件的 `gemini.db`（组件的 admin PATCH 不收 proxy_id，只能改 label/note/status）。代理 URL 在 UI 里是掩码的（`maskProxyUrl`）。
- **登录也走同一出口**：Chrome 的 `--proxy-server` 不支持带认证的代理，所以登录前服务端起一个只监听 127.0.0.1 的 CONNECT 转发（`upstreams/exit-tunnel.ts`，支持 http(s)/socks5 + 用户名密码），Chrome 只拿到本地端口；明文出口地址不出服务端。开窗前先 `probeExit` 一次，连不上直接报错——绝不静默退回直连（否则真实 IP 就暴露了）。`upstreams.loginTunnel.open/close` 配对使用，前端在 `signInGemini` 的 finally 里关掉。
- **防封设置**：`ExitsPanel` 里的并发 / 每分钟 / 每小时 / 熔断冷却 / 两个 fallback 开关，直接读写组件的 `PUT /admin/api/config`（热生效）。默认每个出口并发 5、每分钟 30、每小时 80；出口连续失败 5 次熔断，`proxy_cooldown_min`（默认 120 分钟）后放回；`fallback_direct` 默认 false。
- **熔断展示与自动恢复**：账号行显示绑定的出口、失败次数、`autoDisabledAt`（组件因连续 401/403 自动停用）。`syncFamily` 在「之前 enabled、现在组件报停用、health 映射成 `expired`（组件的 `dead` = fail_count>0）且有错误」时记 `autoDisabledAt` 并把本地 `enabled` 也置 false（用户手动停用映射成 `disabled`，不记；手动启用/停用会清掉这个标记，见 `store.update`）；维护调度器每小时对这类账号 probe 一次，通过就自动启用（用户手动停用的没有这个标记，永远不会被自动打开）。`upstreams.status().warnings` 在账号页顶部提示「某族没有健康账号 / 有账号停用」。
- **掉登录的两种情况与应用自己的保活**（2026-10-21 实测）：① 组件的 rotate 被拒（它不会续 `__Secure-1PSIDTS`，只有 Chromium 在 gemini.google.com 页面上会续）；② 网络断了超过票的寿命（电脑休眠、VPN 切换，日志里 `lookup accounts.google.com … i/o timeout` 或 `wsarecv: An established connection was aborted by the software in your host machine`）。① 能救：桌面版 `geminiRefresh(partition)` 用账号自己的 profile 起无窗口 Chrome、打开 `/app` 停 9 秒（Chromium 自己续期），再读 cookie；前端 `startGeminiKeepalive()`（`boot.tsx` 启动后 30 秒一次、之后每 10 分钟）对 health 是 expired / error / 被组件自动停用的 Gemini 账号调 `recoverGeminiAccount`：拿到新 cookie 就 `upstreams.update { credential, enabled: true }` + probe。每个账号每小时最多一次；登录窗口开着时（同一把 `running` 锁）跳过；cookie 跟上次一模一样就不写。② 救不了（Chrome profile 里的登录也一起死了，用 headless 打开 `/app` 同样没有 `SNlM0e`），只能「重新登录」。判断是哪一种：用 profile 起 headless Chrome 读 1PSIDTS，跟 `gemini.db` 里 `accounts.cookie` 的那份比——一样且都死了就是 ②。
- **粘贴兜底**：`gemini-cookie.ts` 的 `parseGeminiInput`（每行一个账号；整块 Request Headers 只取 `cookie:` 行，`:authority:` 这种 HTTP/2 伪头也跳过；`[{name,value}]` 导出 JSON；`{cookie}`）+ `checkGeminiCookie`（必需六个与组件 `cookie_pool.go` 的报错一致，缺 `.google.com` 那几个就提示「只复制了 gemini 那一栏」，缺 1PSIDTS 只警告）。不齐时「添加」灰掉。
- **组件只听本机**：gemini-web2api-go 默认 `Host: 0.0.0.0`、没有 host 参数，但 `--config` 的 JSON 覆盖默认值（`internal/app/config.go`），启动前在组件目录写 `gemini.json` = `{"host":"127.0.0.1"}`。
- **没自动测的**：真实 Google 登录（会不会被「此浏览器或应用可能不安全」拦）只能真机试；被拦时向导提示改用粘贴。

## 固定本机地址、默认入口与统一下拉（2026-10-21）

- **地址每次重启都变的根因**：桌面版主 HTTP 服务用 `PORT=0`（`desktop/src/server-host.ts`），而 `GatewayService.baseUrl()` 一直引用主服务端口。现在另起一个**独立的 loopback 数据面**（`GatewayService.local`，复用 `gateway/listener.ts`）：只认 `/v1`、`/v1beta`、`/<组>/v1…`、`/healthz`，不开放应用页面、WebSocket、管理 HTTP、缓存垫片和 `~s` 子代理分流。端口存 meta `gateway.localPort`（默认 61697），`gateway.status()` 带 `localBaseUrl / localPort / localRunning / localError`。
- **改端口**走 `gateway.local.set`：先在新端口监听成功，才落盘并换掉旧监听；失败保留旧监听、不写配置、只回错误（不会把地址换成一个起不来的）。切换用 `localSwitch` 串行化，并发请求不会互相覆盖。
- **内部路由不变**：`baseUrl()` 仍是主服务端口 —— 供应商档案、缓存垫片、`~s` 子代理分流继续用它；只有“复制给别人用的地址”改成 `localBaseUrl`。概览里的「不用复制，直接在本应用里用」建/复用 `type:'gateway'` 的供应商（地址和密钥开会话时动态注入，不会再写死一个会变的 URL）。

## Codex 账号的推理来回带 / 强度（2026-11-05，用户反馈「经 Magpie GPT 降智」，要我们自己顶替 Magpie）

- **以前的两个洞**：`anthropic>responses` 翻译时 `R.renderRequest` 根本不写 `reasoning`（强度丢了，Codex 用默认档）；每轮的推理
  item（`encrypted_content`）也被丢，`store:false` 下模型每次工具调用后都从零想起——这就是「降智」。
- **做法**：IR 多一种 part `{type:'reasoning', encrypted, summary}` 和一个事件 `{t:'signature'}`。Codex 回来的 reasoning item →
  Anthropic 思考块（摘要当 thinking 文字、`encrypted_content` 原样当 signature，一个 item 一块）；Claude Code 把思考块带回来时，
  `anthropic.ts blocks()` 用 `detectSignatureProvider(sig) === 'gpt'` 认出它，变回 reasoning item 放在那一轮的工具调用前面。
  请求带 `reasoning {effort, summary:'auto'}` + `include: ['reasoning.encrypted_content']`（`ResponsesRenderOpts.reasoning`，只有网关的
  Codex 路径开；缓存垫片不开——官方 API 对没验证的组织拒绝 summary）。`max` 映射成 `xhigh`。
- **不会串到别家**：`buildOutbound` 对非 Responses 出站把 reasoning part 剥掉；透传到 Claude 的请求由 signature.ts 按 gpt 签名丢块（原有逻辑）。
- **网络**：网关上游本来就走 `net/proxy.ts`（全局设置）和账号自己的 `proxy`，「Magpie 走不了梯子」在原生账号上不存在。
- 测试：`gateway/codex-reasoning.test.ts`。**没有用真账号跑过**——拿到 ChatGPT 账号后看第二轮请求的 input 里有没有 reasoning item、思考强度是否生效。
